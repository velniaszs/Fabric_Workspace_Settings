# Capacity policy — Dataverse tables

Everything that has to exist in Dataverse before any capacity policy flow can be built. **Four tables are created by this project; two existing tables are read and never written.**

Design rationale for all of it is in [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §3. This file is the build sheet — what to create, what to type into each column, and the rules that make the flows work.

> **Nothing is built yet.** Specification, not a description of something that exists.

---

## 0. Rules that apply to every table here

**Create tables and columns in the maker portal. Never by editing [customizations.xml](customizations.xml).** Hand-edited solution XML is how a column ends up with a schema name the designer will not show you and the connector will not offer.

> ### The prefix is `ubsppcoe_`, and it is **not** a placeholder
>
> **Decision 2026-09-07: the four tables this project creates use the `ubsppcoe_` publisher prefix — the same prefix as the platform team's `ubsppcoe_Workspace` and `ubsppcoe_Node`.** Earlier revisions of these documents used `crbab_` and told you to substitute your own. Do not. `crbab_` belongs to the workspace-settings canvas app, which was built on a different platform and is unrelated to policy rules.
>
> **The consequence is that the prefix no longer tells you who owns a table.** Every guardrail in these documents that used to read *"never write a `ubsppcoe_` column"* is now stated **by table name**, because it has to be. The boundary is:
>
> | Never written by any flow | Written by our flows |
> |---|---|
> | `ubsppcoe_Workspace`, `ubsppcoe_Node` | `ubsppcoe_CapacityPolicy`, `ubsppcoe_PolicyDrift` |
>
> If you find yourself reasoning about whether a write is allowed by looking at the prefix, stop — the prefix is the same on both sides of that line now.

**Pick tables and columns from the designer dropdowns rather than typing logical names.** Typed names are the single largest source of the silent failures below, and the shared prefix makes near-miss names much easier to reach for by accident.

**The row key of every table we create is `ubsppcoe_<tablename>id`, generated by Dataverse.** You do not add it. `ubsppcoe_capacitypolicyid`, `ubsppcoe_policyexceptionid`, and so on. **Note that the platform team's two tables do not follow this** — theirs are `ubsppcoe_nodeuniqueid` and `ubsppcoe_workspaceuniqueid` (§1).

**Every table needs a primary name column, and it is never the GUID.** The Fabric GUIDs are ordinary text columns sitting beside the name — `ubsppcoe_nodename` and `ubsppcoe_workspacename` on the platform team's two tables (§1), and the four named in §2–§5 on ours. **No flow reads any of them**; they exist so the grids are legible.

> ### Two logical names now exist on more than one table
>
> Dataverse scopes logical names per table, so this is legal and the flows work. It is still worth knowing before you read an expression and think it is comparing a value with itself:
>
> | Logical name | On the platform team's table | On ours |
> |---|---|---|
> | `ubsppcoe_workspaceid` | `ubsppcoe_Workspace` — the Fabric workspace GUID | `ubsppcoe_PolicyException` — also the Fabric workspace GUID |
> | `ubsppcoe_workspacename` | `ubsppcoe_Workspace` — primary name, the workspace's name | `ubsppcoe_PolicyException` — primary name, also the workspace's name |
>
> Each pair holds the **same kind of value**, which is why the collisions are harmless and arguably helpful — the rebuild joins the two tables on exactly the first one.

> ### Three near-miss names around the Node lookup
>
> These are **different columns on different tables**, and the names differ by a few characters:
>
> | Name | Where | What it is |
> |---|---|---|
> | `ubsppcoe_nodeuniqueid` | on `ubsppcoe_Node` | the **row key**, which is also the Fabric capacity GUID |
> | `ubsppcoe_nodeid` | on `ubsppcoe_Workspace` | the **`Node` lookup**. Filter and read it as `_ubsppcoe_nodeid_value` |
> | `ubsppcoe_node` | on `ubsppcoe_CapacityPolicy` | **our** `Node` lookup. Filter and read it as `_ubsppcoe_node_value` |
>
> All three ultimately hold the same GUID for a given capacity, so a mix-up produces a filter that still *runs*. `_ubsppcoe_node_value` against `ubsppcoe_Workspace` is not a queryable column and returns a `400` — the good outcome. Take the names from the dropdowns.

## 1. The two tables this project does not own

`ubsppcoe_Workspace` and `ubsppcoe_Node` belong to the platform team. **They already exist. Do not create, extend, or write them.** They share our prefix and nothing else — see §0.

| Table | Column | Logical name | Type | Status |
|---|---|---|---|---|
| `ubsppcoe_Node` | Primary name — *Node Name* | `ubsppcoe_nodename` | Text | **Confirmed 2026-09-07.** Display only. **Not** the capacity id |
| `ubsppcoe_Node` | Row key — *Node Unique Id* | `ubsppcoe_nodeuniqueid` | Unique identifier | **Confirmed 2026-09-07. This is also the Fabric capacity GUID** |
| `ubsppcoe_Workspace` | Primary name — *Workspace Name* | `ubsppcoe_workspacename` | Text | **Confirmed 2026-09-07.** Display only |
| `ubsppcoe_Workspace` | Row key — *Workspace Unique Id* | `ubsppcoe_workspaceuniqueid` | Unique identifier | **Confirmed 2026-09-07.** Dataverse only — never sent to Fabric |
| `ubsppcoe_Workspace` | **Fabric workspace GUID** | `ubsppcoe_workspaceid` | Text | **Confirmed 2026-09-07.** This is the Fabric id, not the row key |
| `ubsppcoe_Workspace` | `Node` lookup | `ubsppcoe_nodeid` — read as `_ubsppcoe_nodeid_value` | Lookup → `ubsppcoe_Node` | **Confirmed 2026-09-07.** Its *value* is the Fabric capacity GUID |
| `ubsppcoe_Workspace` | The whitelist flag | `ubsppcoe_oapenabled` | Boolean | **Confirmed 2026-09-07** |

> ### The two tables handle their Fabric GUID in opposite ways
>
> **`ubsppcoe_Node` merges them.** Its row key `ubsppcoe_nodeuniqueid` **is** the Fabric capacity GUID — the platform team supplies it on create rather than letting Dataverse generate one. So a capacity id resolves to a Node row **directly**, with `Get a row by ID`. There is no separate capacity column to find, and no `List rows` + filter needed.
>
> **`ubsppcoe_Workspace` separates them, and names them misleadingly.** Its row key is `ubsppcoe_workspaceuniqueid`; the Fabric workspace GUID is **`ubsppcoe_workspaceid`** — the name that looks like a row key under the usual Dataverse convention. Everything published into `predicate.values` comes from `ubsppcoe_workspaceid`. A row key sent instead is a well-formed GUID that Fabric accepts and then silently never matches — a whole capacity denied, with no error anywhere.

> ### The `Node` lookup therefore holds a Fabric capacity id
>
> A Dataverse lookup stores the target row's key. The target's key is the capacity GUID, so **`_ubsppcoe_nodeid_value` on a workspace row *is* the Fabric capacity id** — and workspaces can be filtered by capacity in one hop:
>
> `_ubsppcoe_nodeid_value eq <capacityId>` — unquoted, as always for a lookup.
>
> This is a coincidence of the platform team's key choice, not a guarantee. If they ever let Dataverse generate Node keys, every filter written this way breaks at once. Prefer routing the value through `ubsppcoe_CapacityPolicy`.`ubsppcoe_node` where a flow already reads that row, so the assumption lives in one place.

> ### No flow writes either table. Ever.
>
> `ubsppcoe_oapenabled` is an internal flag meaning *this workspace has OAP enabled and gets the rest of the Fabric treatment*. Capacity policy is a downstream consumer of it. If a build step wants an `Update a row` against **`ubsppcoe_Workspace` or `ubsppcoe_Node`**, the design has been misread — see [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §3.
>
> **State this by table name, never by prefix.** Since 2026-09-07 our own tables carry `ubsppcoe_` too, so "do not write `ubsppcoe_`" is no longer a rule that means anything.

### The four rules for reading them

**`ubsppcoe_workspaceid` is the Fabric workspace id.** Every whitelist and exception GUID published to Fabric comes from this column and no other. The row key `ubsppcoe_workspaceuniqueid` never leaves Dataverse.

**`ubsppcoe_oapenabled eq true` is the whole whitelist test.** The column is nullable, so `false` and null both compare unequal to `true` and both fall out of the filter. That is the intended behaviour: **neither is added to any rule explicitly**, and rule 1's deny-all is what applies to them. Do not add `and ubsppcoe_oapenabled ne null`, and do not use `ne true` anywhere.

**Filter the lookup as `_ubsppcoe_nodeid_value`, with the leading underscore and the `_value` suffix, against an unquoted GUID.** `ubsppcoe_nodeid eq '…'` is not a queryable column and returns a `400`. Quoting the GUID gives a more confusing error than not.

**Every logical name on these two tables is now confirmed.** Nothing here is a placeholder any more — Q19 is closed. Read them off the portal once anyway if you are building a filter by hand: Settings → Tables → the table → Columns → read the **Logical name** column. An unknown column gives a `400`, but an expression that resolves to blank returns **every row** — which would whitelist every workspace in the tenant on one capacity.

## 2. `Capacity Policies` — one row per governed capacity

| | |
|---|---|
| Display name | `Capacity Policy` / `Capacity Policies` |
| Schema name | `ubsppcoe_CapacityPolicy` |
| Row key | `ubsppcoe_capacitypolicyid` |
| Primary name column | **`ubsppcoe_capacityname`** |
| Ownership | User or team |

| Column | Logical name | Type | Notes |
|---|---|---|---|
| Capacity name | `ubsppcoe_capacityname` | Text (256) | **Primary name.** Written by flow 1 from the trigger input |
| Capacity ID | `ubsppcoe_capacityid` | Text (50) | The Fabric capacity GUID. **The key every flow is invoked with** |
| Node | `ubsppcoe_node` | **Lookup → `ubsppcoe_Node`** | Filter and read it as `_ubsppcoe_node_value`. Set by flow 1 |
| Policy set ID | `ubsppcoe_policysetid` | Text (50) | The Fabric policy set GUID. Written by flow 1 |
| Policy set name | `ubsppcoe_policysetname` | Text (256) | The `pol_<capacity>` display name as created |
| Status | `ubsppcoe_status` | Text (50) | `Active` / `Inactive`. Last known activation status |
| Last rebuild | `ubsppcoe_lastrebuild` | Date and time | Stamped on every successful rebuild |
| Last error | `ubsppcoe_lasterror` | Multiline text (2000) | Blank when healthy. Cleared, not appended, on success |
| Workspace count | `ubsppcoe_workspacecount` | Whole number | OAP-enabled workspaces as of the last rebuild |
| Exception count | `ubsppcoe_exceptioncount` | Whole number | Active exception rows as of the last rebuild |
| Rule count | `ubsppcoe_rulecount` | Whole number | Rules published by the last rebuild, rule 1 included |

### Rules

**`ubsppcoe_node` is a lookup, not a text column.** It stores the Node row GUID, so renaming a node cannot break it, and it lets the rebuild read the policy set id and the Node row in **one** `List rows` call. Read it as `_ubsppcoe_node_value`; plain `ubsppcoe_node` on a `List rows` result is either absent or an expanded object depending on what was selected.

**This table's lookup is `ubsppcoe_node` / `_ubsppcoe_node_value`; the workspace table's is `ubsppcoe_nodeid` / `_ubsppcoe_nodeid_value`.** Different columns, different tables, four characters apart — see the near-miss box in §0. Both resolve to the same capacity GUID, which is what makes comparing them meaningful in [RemoveWorkspaceFromPolicy.md](docs/flows/capacity-policies/RemoveWorkspaceFromPolicy.md) Step 3b.

**`_ubsppcoe_node_value` and `ubsppcoe_capacityid` hold the same GUID**, because the Node row key *is* the Fabric capacity id (§1). Keep both anyway: `ubsppcoe_capacityid` is the key callers pass and survives the Node row being deleted, while the lookup is what enforces that the Node actually exists and gives navigation from the platform team's side. Their agreement is worth checking in the nightly scan — see Q29 in [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §7.

**A blank `ubsppcoe_node` makes the rebuild fail closed.** That is deliberate — see [RebuildCapacityPolicyRules.md](docs/flows/capacity-policies/RebuildCapacityPolicyRules.md) Step 5a. It means the column must be *allowed* to be blank at the schema level, because flow 1 writes it and a partially-created row has to be legible rather than rejected.

**The three counts are a cache, not a source of truth.** They exist so `ListCapacityPolicySets` is one table read instead of a query per capacity. Always render them beside `ubsppcoe_lastrebuild`, or a stale number will be read as current.

**Consider an alternate key on `ubsppcoe_capacityid`.** Flow 1 checks for an existing row and then writes one, with nothing between the two. Two concurrent calls for the same capacity produce two rows and one orphaned policy set in Fabric that nothing maps back to. A uniqueness constraint turns that into a clean failure.

**Do not put these columns on `ubsppcoe_Node` instead.** Ownership, nightly write churn, lifecycle and deletion all decide against it — see [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §3, Q22.

## 3. `Policy Item Types` — the governed item types

| | |
|---|---|
| Display name | `Policy Item Type` / `Policy Item Types` |
| Schema name | `ubsppcoe_PolicyItemType` |
| Row key | `ubsppcoe_policyitemtypeid` |
| Primary name column | **`ubsppcoe_itemname`** |

| Column | Logical name | Type | Notes |
|---|---|---|---|
| Item name | `ubsppcoe_itemname` | Text (100) | **Primary name.** Documentation only; no flow reads it |
| Item type | `ubsppcoe_itemtype` | Text (100) | A Fabric `ItemType` enum value, **sent verbatim** into `predicate.values` |
| Active | `ubsppcoe_active` | Boolean, **default No** | So a type can be retired without deleting history |

### Rules

**`ubsppcoe_itemtype` is passed to Fabric unchanged.** No mapping, no casing fix, no trimming. A typo here produces a rule Fabric accepts and never matches.

**Seed from `fabric_item_types.csv`** in `C:\GIT\ubs-policies` before building the rebuild flow. An empty table means rule 2 is emitted with an empty `item.type` list, which Fabric rejects.

**This table has no effect on rule 3.** Exception rules carry no `item.type` condition at all, so retiring or adding a governed type changes nothing for excepted workspaces.

## 4. `Policy Exceptions` — rule 3, the unrestricted list

| | |
|---|---|
| Display name | `Policy Exception` / `Policy Exceptions` |
| Schema name | `ubsppcoe_PolicyException` |
| Row key | `ubsppcoe_policyexceptionid` |
| Primary name column | **`ubsppcoe_workspacename`** |

| Column | Logical name | Type | Notes |
|---|---|---|---|
| Workspace name | `ubsppcoe_workspacename` | Text (256) | **Primary name**, so the grid is readable. No flow reads it. Same logical name as the primary column on `ubsppcoe_Workspace` (§0) |
| Workspace ID | `ubsppcoe_workspaceid` | Text (50) | The Fabric workspace GUID. **The whole key of the row** |
| Reason | `ubsppcoe_reason` | Multiline text (2000) | Why this workspace is unrestricted |
| Approved by | `ubsppcoe_approvedby` | Text (256) | Who agreed to it |
| Active | `ubsppcoe_active` | Boolean, **default No** | So an exception can be revoked without deleting the history of it |

> **`ubsppcoe_workspaceid` here and `ubsppcoe_workspaceid` on `ubsppcoe_Workspace` are two different columns with the same name and the same meaning** — both are Fabric workspace GUIDs (§0). The rebuild joins on exactly that, so the collision is convenient rather than dangerous. It does mean a `Filter rows` expression is only unambiguous once you know which table the action is pointed at.

### Rules

**There is no capacity column, and adding one is a design change.** The capacity an exception applies to is read from the workspace's `Node` lookup at rebuild time. That is what makes a capacity move behave correctly with no cleanup step — and it is also why an exception follows its workspace without re-approval. Both consequences are argued in [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §3; do not add a `capacity` lookup without reopening Q35.

**`ubsppcoe_active` must default to No.** A row created by hand with the flag untouched is `null`, and the rebuild's `ubsppcoe_active eq true` filter excludes it. Granting nothing is the correct default, but the screen that creates these rows should say so — a new exception that appears to do nothing is almost always an unset flag.

**`ubsppcoe_oapenabled` is not consulted for rule 3.** An exception grants a workspace the platform team has not OAP-enabled. That is deliberate, and it makes this table the only thing in the design that can widen access without the owning team — which is why `ubsppcoe_reason` and `ubsppcoe_approvedby` are columns rather than niceties.

**No flow writes this table.** Rows are created by hand in the maker portal or by the app through the Dataverse connector. **A row edit does not publish itself** — deactivating an exception is not live until that capacity is rebuilt.

**Seed from `fabric_workspaces_exceptions.csv` before cutover.** Rule 3 membership is derived from nothing else, so a migrated exception that was never copied here disappears at the first rebuild — quietly, from a workspace that until then could create anything.

**That flow is the only writer, and the wipe is why.** Anything another flow contributed would vanish at the next scan without warning.

## 6. Who writes what

**By table name, not by prefix** — all six carry `ubsppcoe_`.

| Table | Read by | Written by |
|---|---|---|
| `ubsppcoe_Workspace` | Rebuild, Add, Remove | **Nothing here. Ever** |
| `ubsppcoe_Node` | Initialize (once, to resolve the Node row) | **Nothing here. Ever** |
| `ubsppcoe_CapacityPolicy` | Rebuild, List, Remove, RebuildAll, Sync | Initialize (insert), Rebuild (stamp), Sync (status) |
| `ubsppcoe_PolicyItemType` | Rebuild | **No flow.** Maker portal or app |
| `ubsppcoe_PolicyException` | Rebuild, Remove | **No flow.** Maker portal or app |
| `ubsppcoe_PolicyDrift` | — | Sync only, wipe-and-rewrite |

## 7. Build checklist

1. **No names are outstanding.** Every logical name on `ubsppcoe_Workspace` and `ubsppcoe_Node` was confirmed on 2026-09-07 — Q19 is closed.
2. Create the four tables above in the maker portal, in one solution, using a publisher whose prefix is **`ubsppcoe`**. Not `crbab` — that prefix belongs to the workspace-settings canvas app and has nothing to do with policy rules.
3. Set both `ubsppcoe_active` columns to default **No**.
4. Seed `ubsppcoe_PolicyItemType` from `fabric_item_types.csv`.
5. Seed `ubsppcoe_PolicyException` from `fabric_workspaces_exceptions.csv`, if one is in use.
6. Create the environment variables in [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §6. Their **values** do not reliably travel with a solution export — same caveat as [OPEN-ISSUES.md](docs/OPEN-ISSUES.md) §8.1.
7. Only then start on [GetPolicyToken.md](docs/flows/capacity-policies/GetPolicyToken.md), following the build order in [CAPACITY-POLICY-FLOWS.md](docs/CAPACITY-POLICY-FLOWS.md) §8.
